# Final-year report outline

**Title (working):** Verified tool use for small local language models: a safety-checked MCP calculator with
an empirical study of translation strategies.

## 1. Introduction
* Problem: small local LLMs are unreliable at maths, so tools are used; but they also fail at *calling* tools
  (invented functions, wrong function chosen, malformed output).
* Research questions
  1. How accurate are small local models (7-8B) at turning English word problems into correct expressions?
  2. How much do (a) a fuller prompt, (b) deterministic phrase rewrites and (c) validation-with-feedback retries each
     add? (the ablation: `baseline` -> `prompt` -> `rewrite` -> `full`)
  3. Which kinds of question fail, and why? (error taxonomy: wrong answer / blocked / not-a-calculation / exec error)
  4. What does it cost in latency, and what does a safety policy block in practice?

## 2. Background
MCP (Model Context Protocol), tool calling, structured output, UI automation (accessibility APIs), related work on
LLM tool use and program-aided reasoning.

## 3. System design (use the architecture diagram from the README)
Translator, safety policy, job queue, swappable backends (Python / Windows Calculator), SQLite log + audit trail,
HTTP and stdio transports, dashboard.

## 4. Implementation notes worth a section each
* Safe evaluator without `eval`: AST whitelist, depth/size/exponent limits.
* Verification: results from a backend are compared with an independent evaluator and retried.
* Concurrency: bounded queue, back-pressure instead of blocking, per-job timeout, why UI backends run on one thread.
* Windows Calculator backend and its fragility (button ids depend on version and language).

## 5. Experimental method
* Dataset: 280 template-generated questions in four difficulty levels, reproducible with a fixed seed.
* Models: e.g. `llama3.1:8b`, `qwen2.5:7b` (add others); temperature 0; four strategies.
* Metrics: end-to-end accuracy with 95% Wilson intervals, error taxonomy, retries, latency.
* Procedure: `mcpcalc-bench --models ... --strategies baseline prompt rewrite full`; keep `results.csv` as evidence.
* Sanity check: an oracle that returns the reference expression must score 100% (this validates the dataset,
  evaluator and scoring code, and runs in CI).

## 6. Results and discussion
Tables from `summary.md`, the accuracy-by-strategy chart, accuracy by difficulty, the failure taxonomy, concrete
examples of wrong expressions from `results.csv` (e.g. `power2` chosen for "squared", an invented `deg()`), latency.

## 7. Threats to validity
Template phrasing is narrower than real users; one run per configuration at temperature 0 (say so, or repeat with
several seeds); only two or three models; the oracle only proves the harness, not the models.

## 8. Conclusion and future work
Natural-language-to-tool pipelines need verification, not just a better prompt. Future work: generalise the UI backend
to any application by reading its accessibility tree (e.g. Notepad, Excel), more models, hand-written questions,
user study.

## Likely viva questions
* *Why not just use Python's `math`?* The calculator is a stand-in for any closed application with no API; the project
  is about safe, verified control of such tools by a small local model. The Python backend is the control group.
* *Why is the LLM not allowed to give the answer?* It only translates; execution and verification are separate, so a
  wrong number can never come from the model's own arithmetic.
* *What stops a prompt-injected expression from running code?* The AST whitelist, the function allowlist, size limits
  and no `eval`; every decision is written to the audit log.
* *How do you know the benchmark itself is right?* Reference answers come from an independent evaluator, the file is
  regenerated by a test, and the oracle baseline scores 100%.
